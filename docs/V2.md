# Zenu v2 — the pet is the app

This branch (`v2-pet-companion`) is the ground-up rework of Zenu as a
virtual-pet wellness companion. You choose a companion (Miro, Pip, or
Luma); its needs mirror your reminder timers — it gets thirsty when you
should drink, tired-eyed when you need a screen break, fidgety when you
have sat too long. Caring for it is caring for you. Gentle by design:
the pet asks, it never suffers, and there are no streak-guilt mechanics.
Care moments earn sparks, spent only on cosmetics in the wardrobe.

This document describes the code that actually exists on this branch.

## Architecture

│   ├── completion_event.dart Timestamped care log entry (never pruned)

│   │                         timestamps — never from a live timer

│   │                         last-known-good backup; a corrupt blob is
│   │                         preserved for forensics and never overwritten

├── services/

│   │                         mutation persists, then resyncs the OS
│   │                         notification queue.

## The rules that fix v1's failures

1. **Delivery never depends on the app process where the OS can do it.**
   Android, iOS, and Windows get OS-scheduled notifications (a rolling
   horizon re-derived on every state change, launch, and resume). The
   in-process ticker delivers only on Linux/macOS, and on desktop it
   never pauses on focus loss.
2. **Everything derives from persisted wall-clock timestamps.** Running
   state, per-activity anchors, and snoozes are part of the persisted
   state. A restart, sleep, or reboot changes nothing: the pet wakes up
   already knowing how you're doing, and a running session auto-resumes.
3. **One due-state authority.** `CareService` owns due detection, mood,
   and the notification queue. The UI subscribes; nothing re-implements
   the check.
4. **Loads are non-destructive.** A corrupt blob can cost at most the
   changes since the last successful save — never the whole history.
5. **Failures are visible.** Notification permission is checked and
   surfaced with a recovery action.
6. **Migration, not data loss.** The v1 blob is read once (all three
   legacy shapes), mapped onto the five activities, history carried
   over, and sparks seeded from past completions. The legacy blob is
   left untouched.

## Testing

`flutter test` runs the real suite: schedule math (including the
re-nag roll-forward), store safety (corrupt-blob recovery), legacy
migration (all three shapes), and CareService semantics on a fixed
clock. The old self-referential platform tests and the dead
integration suite were removed rather than kept green.

## Known not-done (honest list)

- iOS builds are untested (no runner config work yet); the scheduling
  lane is shared with Android and stays under the 64-pending cap
  (5 activities x 3 = 15).
- Linux/macOS still deliver in-process (no OS scheduler in the plugin);
  the ticker no longer pauses, so delivery works while the app runs.
- No sound design, no Rive/Lottie — the pet is 100% CustomPainter.
- Wardrobe items render on the pet for scarf/glasses/crown/cap/charms;
  more slots need painter work.
- Statistics are intentionally minimal (today + 14-day rhythm) — the
  unbounded event log is in place for richer views.
